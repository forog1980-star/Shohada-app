# گزارش فنی ۰۱ — طراحی اولیه سیستم کاربران، نقش‌ها، مجوزها و ردیابی فعالیت‌ها

**تاریخ:** 2026-10-07  
**دامنه:** معماری مرکزی کاربران سامانه  
**شاخه توسعه مستندات:** `docs/user-access-control-20261007`  
**مبنای بررسی:** شاخه `qa` پروژه `forog1980-star/Shohada-app`

---

## ۱. هدف

در این مرحله تصمیم گرفته شد سیستم User که ابتدا برای بخش «کنترل کیفیت داده» در نظر گرفته شده بود، به یک **هسته مرکزی کاربران کل سامانه** ارتقا پیدا کند.

بنابراین از این پس کنترل دسترسی تمام بخش‌های سامانه باید بر پایه یک مدل مشترک User → Role → Permission انجام شود.

این طراحی باید بدون ایجاد وابستگی متقابل بین ماژول‌ها و بدون شکستن نسخه عملیاتی فعلی توسعه پیدا کند.

---

## ۲. تصمیم معماری اصلی

### مدل قبلی

کاربر و نقش‌ها در محدوده کنترل کیفیت داده تعریف می‌شدند.

### مدل جدید

یک سیستم مرکزی برای کل سامانه ایجاد خواهد شد:

```
User / Account
      ↓
Roles
      ↓
Permissions
      ↓
Permission Engine
      ↓
Application Modules
```

ماژول‌های اصلی مانند جستجو، ثبت اطلاعات، بهسازی، کنترل کیفیت، آمار و گزارش‌ها از همین هسته استفاده خواهند کرد.

---

## ۳. User

هر فردی که اجازه ورود به سامانه داخلی را دارد باید حساب مستقل و قابل شناسایی داشته باشد.

اطلاعات پایه مورد نیاز در طراحی:

- شناسه یکتا
- نام و مشخصات نمایشی
- نام کاربری/روش ورود
- وضعیت حساب
- نقش‌ها
- مجوزهای مؤثر
- تاریخ ایجاد
- آخرین ورود
- وضعیت فعال/غیرفعال
- اطلاعات لازم برای Audit

در سامانه اصلی، استفاده از Anonymous Sign-in نباید مبنای هویت کاربران عملیاتی باشد.

---

## ۴. Role

Role نمایانگر نقش کاری یا سازمانی کاربر است.

نمونه‌های اولیه برای بررسی:

- مدیر سامانه
- مدیر
- اپراتور
- کارشناس ثبت اطلاعات
- کارشناس بهسازی
- کارشناس کنترل کیفیت
- ناظر
- تأییدکننده
- گزارش‌گیر
- مشاهده‌گر

این فهرست در مرحله طراحی Permission نهایی خواهد شد.

یک User می‌تواند در آینده بیش از یک Role داشته باشد.

---

## ۵. Permission

Permission مجوز انجام یک عملیات مشخص است و نباید صرفاً بر اساس نام Role کنترل شود.

نمونه:

```
martyrs.view
martyrs.create
martyrs.edit
martyrs.delete

rehabilitation.view
rehabilitation.create
rehabilitation.edit
rehabilitation.approve

quality.view
quality.submit
quality.review
quality.approve
quality.reject

reports.view
reports.export

users.view
users.create
users.edit
users.disable

roles.view
roles.create
roles.edit
roles.delete
```

فهرست نهایی Permissionها پس از استخراج عملیات واقعی تمام ماژول‌های سامانه تعیین خواهد شد.

---

## ۶. Permission Engine

منطق مجوزها باید مرکزی باشد و در فایل‌ها و صفحات مختلف تکرار نشود.

الگوی مفهومی:

```
can(user, "martyrs.edit")
can(user, "quality.review")
can(user, "quality.approve")
can(user, "reports.export")
```

تمام ماژول‌ها باید در نهایت از همین منطق مشترک استفاده کنند.

---

## ۷. کنترل کیفیت داده

کنترل کیفیت دیگر دارای سیستم User مستقل نخواهد بود.

Workflow پیشنهادی:

```
Detection / Submission
        ↓
Submitter
        ↓
Reviewer
        ↓
Approver
        ↓
Controlled Apply
        ↓
Audit Log
```

تفکیک Reviewer و Approver از نظر معماری حفظ می‌شود، حتی اگر در مرحله اول یک فرد هر دو مسئولیت را داشته باشد.

---

## ۸. AI

AI یک User انسانی و یک Role سازمانی محسوب نمی‌شود.

AI می‌تواند:

- مغایرت را شناسایی کند.
- رکوردهای مشکوک را پیدا کند.
- پیشنهاد اصلاح ارائه کند.
- شواهد و توضیح ارائه کند.
- گزارش تولید کند.

اما نباید صرفاً با داشتن یک Permission عادی مستقیماً اطلاعات اصلی `martyrs` را تغییر دهد.

اعمال تغییر باید از Workflow کنترل‌شده عبور کند.

---

## ۹. Audit Log

ردیابی فعالیت‌ها به‌عنوان جزء اصلی معماری کاربران تصویب شد.

برای فعالیت‌های مهم حداقل این اطلاعات باید قابل ثبت باشد:

- کاربر
- زمان
- ماژول
- عملیات
- موجودیت/رکورد هدف
- نتیجه عملیات

برای عملیات حساس، طراحی باید امکان ثبت موارد زیر را نیز در نظر بگیرد:

- مقدار قبل
- مقدار بعد
- دلیل/یادداشت
- شناسه نشست
- فراداده امنیتی مناسب

Audit باید در سطح امن سامانه ثبت شود و صرفاً به لاگ رابط کاربری وابسته نباشد.

---

## ۱۰. مدیریت کاربران

مدیر مجاز سامانه باید در آینده بتواند کاربران را مدیریت کند و برای هر کاربر Role و Permission مناسب تعیین کند.

مدل پیشنهادی:

```
User
  ├── Role A
  ├── Role B
  └── Permission Overrides
```

Permissionهای مستقیم کاربر فقط در صورت نیاز و با کنترل مدیریتی استفاده خواهند شد.

---

## ۱۱. تفکیک Admin و Approver

این دو مفهوم نباید به‌صورت خودکار یکی فرض شوند.

```
Admin ≠ Final Approver
```

مدیر سامانه می‌تواند مسئول مدیریت حساب‌ها و تنظیمات باشد، اما دسترسی تأیید نهایی داده باید یک Permission مستقل و صریح باشد.

---

## ۱۲. امنیت نسخه عمومی و نسخه داخلی

نسخه فعلی GitHub و داده‌های عملیاتی باید از نظر دسترسی از هم تفکیک شوند.

Public بودن کد Repository نباید به معنی Public بودن موارد زیر باشد:

- اطلاعات کاربران
- داده‌های عملیاتی
- Role/Permission
- Audit Log
- عملیات حساس
- Credentialها
- Service Role / Secretها

هیچ Secret یا Service Role Key نباید در Frontend عمومی قرار گیرد.

---

## ۱۳. وضعیت تغییرات در این مرحله

### انجام شد

- ارتقای User از یک قابلیت محدود کنترل کیفیت به هسته مرکزی سامانه
- تعریف مفهومی User / Role / Permission
- تصمیم به مرکزی بودن Permission Engine
- اضافه شدن Audit Log به معماری مرکزی
- حفظ تفکیک Reviewer / Approver
- تعیین جایگاه AI به‌عنوان عامل تحلیلی، نه کاربر انسانی

### انجام نشد

- تغییر Supabase
- تغییر Supabase Auth
- تغییر RLS
- تغییر Policy
- ایجاد جدول جدید
- تغییر جدول `martyrs`
- تغییر کد عملیاتی
- تغییر نسخه عمومی GitHub
- فعال‌سازی Login واقعی

---

## ۱۴. مرحله بعد

قبل از هر پیاده‌سازی، مراحل زیر انجام می‌شود:

1. استخراج ماژول‌های واقعی سامانه.
2. استخراج عملیات واقعی هر ماژول.
3. طراحی ماتریس Permission نهایی.
4. طراحی Roleهای پایه.
5. طراحی Role سفارشی.
6. طراحی User/Account و وضعیت حساب.
7. طراحی Authentication و Session.
8. طراحی Audit Log.
9. طراحی Authorization و RLS.
10. بررسی امنیتی و تأیید معماری.
11. ایجاد Recovery Point.
12. شروع پیاده‌سازی حداقلی و قابل بازگشت.

**تا قبل از تأیید معماری، هیچ تغییر عملی در داده، Auth، RLS یا Policy انجام نمی‌شود.**

---

## ۱۵. معیار پایان این بخش

این بخش زمانی از مرحله طراحی خارج می‌شود که:

- Permissionهای واقعی تمام ماژول‌ها مشخص شده باشند.
- Roleها و ارتباط آنها با Permissionها مشخص شده باشد.
- مدل User/Account تأیید شده باشد.
- Login و Session طراحی شده باشد.
- Audit Log طراحی شده باشد.
- مسیر کنترل دسترسی از UI تا Backend/Database مشخص شده باشد.
- الزامات امنیتی و RLS مشخص شده باشد.
- وابستگی آن با کنترل کیفیت داده مشخص شده باشد.
- معماری توسط مالک پروژه تأیید شده باشد.

تا آن زمان این بخش **در وضعیت Design / Architecture قرار دارد و Production Ready اعلام نمی‌شود.**
