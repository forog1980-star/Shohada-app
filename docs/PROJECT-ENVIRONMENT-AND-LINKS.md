# تعریف رسمی نسخه‌ها، لینک‌ها و روش کار پروژه Shohada-app / GolzarStone

## 1. هدف این سند
این فایل تعریف رسمی و قابل مراجعه پروژه برای تشخیص این است که هر نسخه کجا قرار دارد، کدام لینک برای تست است، کدام لینک عملیاتی است و تغییرات از چه مسیری باید وارد پروژه شوند.

این تعریف برای جلوگیری از اشتباه بین QA و main، جلوگیری از اعمال اصلاح روی نسخه اشتباه و حفظ امکان بازگشت به نسخه سالم ثبت شده است.

---

## 2. تعریف نسخه‌ها

### QA — نسخه مرجع تست و توسعه
**Branch:** `qa`

QA نسخه‌ای است که توسعه، اصلاح، آزمایش و رفع ایرادهای جدید در آن انجام می‌شود.

قواعد:
- تغییرات جدید ابتدا در QA انجام می‌شود.
- QA محل تست عملی کاربر و تست فنی است.
- تا وقتی یک تغییر در QA تأیید نشده، وارد main نمی‌شود.
- QA می‌تواند موقتاً شامل اصلاحات در حال آزمایش باشد.
- داده‌های Supabase در QA، مگر با ضرورت مشخص، فقط read-only استفاده می‌شوند.
- قبل از تغییر مهم، Recovery Point ایجاد می‌شود.

### main — نسخه مرجع عملیاتی
**Branch:** `main`

main نسخه مرجع عملیاتی پروژه است.

قواعد:
- main محل آزمایش و خطا نیست.
- تغییر مستقیم و آزمایشی روی main ممنوع است.
- فقط تغییر تأییدشده از مسیر QA و پس از تست وارد main می‌شود.
- لینک عملیاتی همیشه باید بر اساس main منتشر شود.
- Force reset و force push روی main ممنوع است.

## 3. لینک‌های رسمی پروژه

### 3-1. لینک عملیاتی — MAIN
**کاربرد:** استفاده عملیاتی و ارائه به نیروها

`https://forog1980-star.github.io/Shohada-app/`

این لینک فقط باید نسخه منتشرشده از **main** را نمایش دهد.

### 3-2. لینک تست — QA
**کاربرد:** توسعه، رفع ایراد و تست عملی

`https://shohada-app-git-qa-forog1980-8339.vercel.app/`

این لینک برای نسخه **qa** در Vercel در نظر گرفته شده است. اگر Vercel پس از ایجاد/به‌روزرسانی branch آدرس Preview دیگری ارائه کند، آدرس ثبت‌شده در GitHub/Vercel باید با همین تعریف جایگزین شود؛ معیار، اتصال لینک به branch `qa` است، نه نام ظاهری URL.

> نکته: لینک QA نباید به عنوان نسخه عملیاتی به نیروها معرفی شود.

---

## 4. index.html و master-loader.js

`frontend/index.html` نقطه ورود برنامه است و `frontend/master-loader.js` مسئول بارگذاری زنجیره اصلی ماژول‌هاست.

این دو فایل «نسخه مرجع» نیستند؛ نسخه مرجع را Branch و Deployment مشخص می‌کند.

مسیر کلی برنامه:

`لینک → Deployment → Branch → frontend/index.html → master-loader.js → app.js و ماژول‌ها → Supabase`

بنابراین اگر بین دو نسخه اختلافی وجود داشت، ابتدا باید Branch و Commit مربوط به Deployment بررسی شود.

---

## 5. چرخه اجباری تغییرات

چرخه استاندارد:

`Recovery/Backup → Diagnose/Check → Minimal Change → Recheck → Technical Test → Deployment/Version Check → Practical User Test → Final Confirmation`

مسیر شاخه‌ای:

`qa → تست فنی → لینک QA → تست عملی کاربر → تأیید → main → لینک عملیاتی`

هیچ تغییر آزمایشی نباید مستقیم روی main انجام شود.

---

## 6. Recovery و بازگشت

قبل از هر تغییر مهم باید یک Recovery Point یا Recovery Branch ایجاد شود.

هدف Recovery این است که اگر تست شکست خورد، بتوانیم دقیقاً به نقطه سالم قبل از تغییر برگردیم و مجبور نباشیم پروژه را از ابتدا بازسازی کنیم.

Recoveryهای مربوط به تغییرات اخیر:
- `recovery/main-before-statistics-fix-20260919`
- `recovery/main-before-navigation-fix-20260919`
- `recovery/main-before-pages-release-20260915`
- `recovery/main-before-integration-20260915`

Recoveryها تا تثبیت نسخه جدید و تأیید بهره‌برداری حذف نشوند.

---

## 7. قانون Pull Request و Merge

1. تغییر در QA انجام می‌شود.
2. تست فنی انجام می‌شود.
3. لینک QA بررسی می‌شود.
4. تست عملی توسط کاربر انجام می‌شود.
5. ایرادها اصلاح و دوباره تست می‌شوند.
6. پس از PASS، Pull Request به main آماده می‌شود.
7. پس از تأیید نهایی، Merge انجام می‌شود.
8. GitHub Pages از main Deploy می‌شود.
9. لینک عملیاتی بررسی می‌شود.

---

## 8. آمار، داده و Supabase

کد برنامه و داده عملیاتی دو موضوع جدا هستند.

- اصلاح کد در QA نباید به معنی تغییر خودکار داده Supabase باشد.
- در QA/Release، Supabase تا حد امکان read-only باقی می‌ماند.
- هر تغییر داده یا Schema باید جداگانه ثبت و قابل بازگشت باشد.
- آمار برنامه باید با تعریف عملیاتی مصوب تطبیق داده شود و صرفاً از روی یک عدد ظاهری UI نتیجه‌گیری نشود.

---

## 9. پاک‌سازی فایل‌ها

فایل قدیمی فقط زمانی حذف می‌شود که:
1. در نسخه فعال هیچ مرجع اجرایی به آن وجود نداشته باشد؛
2. وظیفه آن توسط فایل دیگری جایگزین شده باشد؛
3. Recovery یا مستندات تاریخی به آن نیاز نداشته باشند؛
4. حذف آن با تست فنی و مسیر بازگشت همراه باشد.

فایل‌های صرفاً قدیمی یا دارای نام «fix» بدون بررسی وابستگی حذف نمی‌شوند.

---

## 10. قانون تشخیص نسخه هنگام شروع هر کار

در ابتدای هر کار باید این چهار مورد مشخص شود:

- **نسخه مرجع تست:** `qa`
- **نسخه مرجع عملیات:** `main`
- **لینک تست:** Vercel Preview متصل به `qa`
- **لینک عملیات:** GitHub Pages متصل به `main`

سپس Commit فعلی هر Branch با Deployment مورد استفاده تطبیق داده شود.

این قانون از این پس مبنای ادامه پروژه است.
